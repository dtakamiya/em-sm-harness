# 先回り検知の仕様（期限接近・ブロッカー・返信待ち・会議準備・放置）

状態: モック試作済み（emh-036・§4 の 8 項目はテスト済み）。設計は emh-017・条件付き GO。判断の背景と別案は [ADR 0003](../adr/0003-proactive-detection.md)。しきい値は全て仮置きで、EM の使用感で調整する（Q-021〜Q-023）。サンプルは全て架空。

## 結論
- EM が `scripts/proactive_scan.py` を走らせたときだけ動く（常駐・cron なし）。読み取りは tasks・Jira キャッシュ・会議一覧。書くのは状態ファイルだけで、外部への送信・更新はしない（L1）
- 検知は 5 種・重要度は **高 / 中 / 低の 3 段**（点数化しない）・1 回の表示は **最大 5 件**（催促は 3 件まで）
- 通知を絞る要点: **高は毎回出す／中は 2 営業日おき／低は週 1 の要約**。同じ件を何度も押し付けない

## 1. 検知ルール
| # | ルール | 入力 | 条件（既定） | 段 |
|---|---|---|---|---|
| 1 | 期限接近 | tasks の `due` | open/doing で超過・今日 → 高 / 3 日以内 → 中（17 の帯と同じ） | 高・中 |
| 2 | ブロッカー | Jira キャッシュの blocks リンク | 止めている側が未完了で 3 営業日更新なし → 中。止められている側に 3 日以内の期限（tasks）があれば高 | 中・高 |
| 3 | 返信待ち | tasks の `waiting` / `next_check` | 17 のまま。3 回目は催促でなく判断依頼 → 高 | 中・高 |
| 4 | 会議準備 | EM が貼る会議一覧（`meetings.json`・Q-023） | 翌営業日までに会議があり、準備タスクが無い／未完了 → 中 | 中 |
| 5 | 放置 | Jira 進行中 / tasks | Jira 進行中が 7 営業日更新なし（Q-022）、個人タスクは 14 日動きなし → 低 | 低 |

- Jira の期限はキャッシュに無い（[06](06-cache-schema.md)）。期限は tasks の `due` とスプリント終了日のみを使う
- 各ルールは純関数 `検知(入力, 今日, 設定) → 所見の一覧`。所見は `{key, rule, ref, level, fact}`、`key = ルール:対象`（例 `due:t-0003`）
- 出力に書くのは **事実だけ**（「N 営業日 更新なし」）。理由・原因は推測しない。ブロッカーと放置の併発は共起として並べ、因果と書かない
- 他者担当の件は担当者の識別子を出さない（「担当: 他メンバー」）。評価語（遅い・放置している 等）を使わない

## 2. まとめ方と通知の絞り方
| 項目 | 規則 |
|---|---|
| 表示上限 | 先回り合計 5 件。高を先に取り、超過は「ほか N 件」。催促は 3 件まで（17） |
| 並べ順 | 段 → [17](17-task-priority-and-waiting.md) の 4 段（帯・priority・blocks・期限・id）。決定的 |
| まとめ | 同じ対象は複数ルールに当たっても 1 行（ルール名を併記） |
| 朝の計画での既出の畳み（emh-057 = 朝の計画の重複整理の起票番号） | `morning_plan.py --proactive` だけ。次の 3 つを先回り節で 1 行（「既出のため畳んだ件: ID・ID」）に畳む: ① 期限接近だけ・段が中・対象が「今日やる順」にある ② 期限接近だけ・期限超過・対象が今日やる順にある（行に「期限超過 N 日」が出て、結論行も 🔴 になる）③ 返信待ちだけ・対象が「催促候補」にある（行に待ち先・確認予定・催促回数が出る）。**畳まない**: 期限が今日の高（結論行が 🟢 のままで、強調が消えるため）・ブロッカー等ほかのルールを含む件・判断依頼・今日やる順に無い件。畳んでも各件は上の節に必ず残り、結論行は変わらない。単独の `proactive_scan.py` は畳まない |
| 畳む件と上限 | 畳む判定は上限 5 件・催促 3 件を数える**前**に行い、畳んだ件は枠を使わない。畳まれない新情報が「ほか N 件」に押し出されない |
| 畳む件と表示回数 | 畳んだ件は表示済みに**数えない**（状態に回数・最終表示日を残さない）。その後に今日やる順から外れたら、中の 2 営業日抑止を受けずに先回りへ出る |
| 高 | 抑止しない。解消するまで毎回出す |
| 中 | 同じ key は 2 営業日出さない。段が上がったら再掲 |
| 低 | 日次では出さず、週 1 回の要約実行（`--digest`）でまとめる |
| 昇格 | 中・低が 3 回表示されても未対応なら判断依頼（keep / drop・おすすめ付き）にし、以後は繰り返さない |
| 既読・スヌーズ | `--ack <key>`（同じ段の間は非表示）/ `--snooze <key> <日付>`（既定 2 営業日）。高でも EM が明示したら尊重 |
| 除外 | done / dropped、直近 1 営業日に EM が操作した件 |
| 0 件 | 「先回り対応不要」の 1 行 |

## 3. 実行モデル
- 起動: `python3 scripts/proactive_scan.py [--today 日付] [--digest] [--ack K] [--snooze K 日付]`
- 出力: 標準出力の Markdown（結論 → EM がやること → 先回り → 判断依頼 → 詳細）。[14](14-output-quality-checklist.md) の A（60 秒）・B（事実と解釈）を満たす
- 終了コード: 0 = 通知なし / 10 = 通知あり / 2 = 入力ファイル破損（状態を変えず中止）
- 状態: `data/state/proactive.json` = `{key: {first_seen, last_shown, shown_count, level, snooze_until, acked_level?, decision_on?}}`（`acked_level` = `--ack` した段。同じ段の間は非表示 / `decision_on` = 判断依頼にした日。以後は繰り返さない）。key と回数だけ（本文・実名は入れない）。一時ファイル → rename、`.bak` を 1 世代。90 日で、解消済みの key を削除。状態が壊れたら全 key を新規扱いにして出し直す（通知が増える側に倒す）
- 冪等: 同じ入力・日付・状態なら出力は同一。同日の再実行は表示済みを再表示し、回数を増やさない
- 欠損: 入力ファイルが無いルールは「入力なし」を詳細に 1 行出して他は続行（沈黙で「問題なし」と誤読させない）。Jira キャッシュの `fetched_at` が 2 営業日超なら「データが古い」を 1 行
- 操作は `data/audit/YYYY-MM-DD.jsonl` に 1 行追記: `{at, op, key}`（`op` = `ack` / `snooze`。key と操作名のみ）
- 入力の検証: tasks・Jira キャッシュ・会議一覧の型・必須項目（`status` / `updated` / `fetched_at` / `start` 等）・日付形式が不正なら終了コード 2（`--snooze` / `--today` の日付不正も同じ。状態は変えない）。`title` / waiting の `waiting_on` / リンクの `issue_key` の型、状態ファイルの値が辞書でないときも同じ（状態ファイルは読めないだけなら新規扱い、形が違えば上書きしない）。`morning_plan.py --proactive` は出力を組み立てた後にだけ状態を保存する。tasks.json が無いときも「入力なし」を詳細に 1 行出す

## 4. 受け入れ基準（実装時）
1. `due` が今日 + 3 日は中で出る。+4 日は出ない（境界）
2. 同じ入力を 2 回実行して出力が一致し、`shown_count` が増えない
3. nudge 履歴が 2 回の返信待ちは、下書きでなく判断依頼になる
4. 先回りが 8 件なら 5 件 + 「ほか 3 件」。催促は 3 件で止まり、高が先
5. **期限超過が 3 回以上表示されても消えない**（高は抑止しない）
6. 会議一覧が無いとき、会議準備だけ「入力なし」1 行で他は通常出力
7. tasks.json が破損なら終了コード 2・状態不変
8. 出力に担当者識別子・評価語を含まない
9. （emh-057）朝の計画で、既出の件を畳んでも結論行は同じ・畳んだ ID が上の節に全て残り・新情報（ブロッカー）は畳まれない（`tests/test_morning_plan.py` FoldAlreadyShownTest。架空サンプルで先回り節 4 行 → 2 行。畳んだ件が上限枠を使わない・表示回数に数えないことも同テストで確認）。注: EM が 60 秒で読めるかは**未計測**（EM の使用感で確認する）
