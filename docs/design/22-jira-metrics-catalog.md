# Jira 指標カタログ（emh-004）

状態: ドラフト（設計のみ・実接続なし）。入力は [06](06-cache-schema.md) のスキーマだけ。値はすべて架空例。
使い道: S1 スプリント健全性（[12](12-secretary-job-list.md)）・D4 先回り検知（[18](18-proactive-detection.md)）・S3 レトロの材料。

## 1. 共通ルール（全指標）
- 指標は**判断材料**であり、判定ではない。出力は「観察（事実）」+「解釈の候補（最大 2 つ）」に分ける（[14](14-output-quality-checklist.md) B1〜B4）
- 共起は原因と書かない。原因らしきものを書くときは「共起」と明記し、確認方法（誰に何を聞くか）を添える（14 C1・C2）
- 出力には必ず 1 行で**限界**を添える（14 C3）: 対象件数 N・期間・取得が完全か（`complete: false` なら指標を出さず「再取得が必要」と報告）
- **N < 5 の指標は件数のみ**を示し、割合・平均・傾向を出さない（少人数・少件数の割合は 1 件で大きく動く）
- 個人別の指標は作らない。人の評価に転用されやすいため、担当者に紐づく数字は分布（§2.5）に限る
- 日数は**営業日**で数え、起点は各指標で明記する（営業日カレンダーは `config/local.*`。無ければ暦日で数えて「暦日」と明記）

## 2. 指標
### 2.1 ステータス滞留
| 項目 | 内容 |
|---|---|
| 判断材料 | 動いていない課題に気づく（D4 の放置検知、S1） |
| 計算 | 現在の status に入った `at`（status 遷移の最新）から `fetched_at` までの営業日。遷移が TTL で消えた古い課題は `updated` を代用し「更新日基準」と明記 |
| 必要 | `status` / `status_category` / `transitions[field=status]` / `updated` |
| 誤読リスク | ①`updated` はコメント等でも動く（実作業の有無ではない）②「待ち」ステータスの滞留は正常（レビュー待ち等）③大きい課題は長くて当然 |
| 出し方 | しきい値は [18 §1](18-proactive-detection.md)（進行中 7 営業日・Q-022）。「滞留が長い」でなく「N 営業日動きなし」と事実で書く |

### 2.2 見積もり乖離
| 項目 | 内容 |
|---|---|
| 判断材料 | 計画の精度と、見積もり変更の頻度（プランニング改善の材料） |
| 計算 | スプリント開始時点の SP と現在の SP の差（`transitions[field=story_points]` の開始日以前の最後の `to`）。完了済み課題の合計 SP とスプリント初期コミットの比も参考に出す |
| 必要 | `story_points` / `transitions[field=story_points]` / `sprints[].start` |
| 誤読リスク | ①SP は相対値でチーム間比較不可②SP 無し（`null`）と 0 は別（06 §1）。`null` は除外して件数を明記③途中で分割した課題は乖離に見える④完了時 SP を後から直す運用だと乖離が消える |
| 出し方 | 差の大きい課題を 3 件までキーで列挙。「見積もりが甘い」とは書かない |

### 2.3 スコープ変動
| 項目 | 内容 |
|---|---|
| 判断材料 | スプリント途中の追加・除外の量（S5 ゴール変更の判断材料） |
| 計算 | `transitions[field=sprint]` のうち、スプリント開始後の `at` で入った件数（追加）と出た件数（除外）。SP 合計も併記。繰り越し（前スプリントから持ち越し）は別カウント |
| 必要 | `transitions[field=sprint]` / `sprints[].start・end・state` / `story_points` |
| 誤読リスク | ①開始日の直後の整理は計画の一部で変動ではない（開始から 1 営業日は猶予として除外。調整可）②緊急対応の追加と計画漏れは区別できない③除外は「完了で抜けた」とは限らない |
| 出し方 | 追加 / 除外 / 繰り越しを別行で。理由は書かない（不明）。聞く問いを添える（「追加分の経緯は？」） |

### 2.4 ブロッカー
| 項目 | 内容 |
|---|---|
| 判断材料 | 他に止められている作業の把握（D4、S1） |
| 計算 | `flagged: true` の課題、および `links[link_type=blocks, direction=inward]` で未完了（`status_category != done`）の課題に塞がれているもの。塞いでいる側が `done` なら対象外 |
| 必要 | `flagged` / `links[]` / `status_category` |
| 誤読リスク | ①リンクは貼られていなければ見えない（無いことは安全の証拠ではない）②リンク先が別プロジェクトだと取得範囲外で状態不明（「不明」と書く）③`flagged` は付けっぱなしがある（滞留とあわせて見る） |
| 出し方 | 「塞いでいる課題が何件目か」の連鎖を 1 段まで。原因の推測はしない |

### 2.5 担当偏り（分布のみ）
| 項目 | 内容 |
|---|---|
| 判断材料 | 負荷が特定の人に寄っていないかの気づき（プランニングの容量材料 S2） |
| 計算 | 進行中の課題数・SP 合計の**担当者別分布**から「最大の担当に集中する割合」と「担当なし（`assignee_ref: null`）の件数」だけを出す。`assignee_ref` は表示名に戻さず、出力では「担当 A / B」と**その場限りの記号**にする（回をまたいで同一視しない） |
| 必要 | `assignee_ref`（現在値のみ。遷移は持たない・06 §2）/ `status_category` / `story_points` |
| 誤読リスク | ①課題の大きさ・難しさは課題数に出ない②兼任・サポート作業は Jira に現れない③少人数だと 1 人の休暇で分布が崩れる④「多い人」が成果の多い人とは限らない |
| 出し方 | N < 5 は出さない。個人名・個人の時系列は出さない。structured（90 日保持）に `assignee_ref` を持ち込まない（06 §4）。再アサイン履歴の分析は評価転用リスクが高いため**やらない**（必要になれば EM 承認で 06 の版を上げる） |

## 3. 出力の型（S1 に組み込む）
```
スプリント健全性（<project_alias>・<日付>・N=<件数>・取得: 完全）
観察
- 滞留: 進行中 12 件のうち 3 件が 8 営業日以上動きなし（EX-101, EX-104, EX-110）
- スコープ: 開始後に追加 2 件(計 5SP)・除外 1 件(2SP)・繰り越し 3 件
解釈の候補
- 追加 2 件は緊急対応、または計画漏れ（どちらかは Jira から分からない）
聞く問い: EX-101 は誰かの返答待ちか。追加 2 件の経緯は。
限界: SP 無し 2 件は除外。レビュー待ちの滞留は正常な場合がある。
```
