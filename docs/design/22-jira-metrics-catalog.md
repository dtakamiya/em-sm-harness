# Jira 指標カタログ（emh-004）

状態: ドラフト（設計のみ・実接続なし）。入力は [06](06-cache-schema.md) のスキーマだけ。値はすべて架空例。

## 結論
- 5 指標（滞留・見積もり乖離・スコープ変動・ブロッカー・担当偏り）を「判断材料・計算・必要フィールド・誤読リスク」で定義した。どれも**判定ではなく材料**で、出力は事実 + 解釈の候補にする
- 担当偏りは安全側に絞る: **担当者が 3 人未満なら出さない**（固定・調整対象外）。出すのは集中割合と担当なし件数だけ。個人名・個人別の並びは出さない
- 計算は決定的スクリプトで行い、LLM に数えさせない。実装は別タスク（§5 の受け入れ基準が出発点）
- 滞留の起点（Q-026）とスコープ変動の猶予日数（Q-027）は Ryoko が既定を決定済み（どちらも可逆）。EM が覆したい場合のみ回答で上書き

用語: **SP** = ストーリーポイント（見積もりの相対値）。**TTL** = キャッシュの保持日数（14 日・[06 §4](06-cache-schema.md)）。**emh-004** = この設計の backlog ID。**S1〜S5** = 秘書の仕事の番号（[12](12-secretary-job-list.md)）。

使い道: S1 スプリント健全性（先回り分類）・S2 プランニングの容量材料・S5 ゴール変更判断の材料・D4 先回り検知（[18](18-proactive-detection.md)）・S3 レトロの事実の材料。

## 1. 共通ルール（全指標）
- 出力は「観察（事実）」+「解釈の候補（最大 2 つ）」に分ける（[14](14-output-quality-checklist.md) B1〜B4）。共起を原因と書かない。原因らしきものは「共起」と明記し、確認方法（誰に何を聞くか）を添える（14 C1・C2）
- 出力には 1 行で**限界**を添える（14 C3）: 対象件数・期間・取得が完全か。`complete: false` なら指標を出さず「再取得が必要」と報告する
- **件数 N < 5 は件数だけ示し、割合・平均・傾向を出さない**。N = 母集団の課題数（その指標の対象課題）。例外: 担当偏りは §2.5 の別条件が優先（N < 5 の件数表示すら出さない場合がある）
- 人に関する出力は 14 D1（人を属性で括らない）・D3（個人別の時系列・ランキングを作らない）に従う。担当者に紐づく数字は §2.5 の分布に限る
- **1on1（O1〜O4）には流用しない**。この指標群は個人の評価材料ではなく、チームの状況把握用。1on1 の材料はタスクと本人の発言から作る
- 日数は営業日（営業日カレンダーは `config/local.*`。無ければ暦日で数え「暦日」と明記）。起点は指標ごとに明記する

## 2. 指標
### 2.1 ステータス滞留
| 項目 | 内容 |
|---|---|
| 判断材料 | 動いていない課題への気づき（D4 の放置検知、S1） |
| 計算 | **既定は [18 §1](18-proactive-detection.md) ルール 5 と同じ `updated` 基準**: `updated` から `fetched_at` までの営業日。補助として、現在の status に入った `at`（status 遷移の最新）からの営業日を併記できる（遷移が TTL で消えた課題は併記しない）。どちらを主にするかは Q-026 |
| 必要 | `status` / `status_category` / `updated` / `transitions[field=status]` |
| 誤読リスク | ①`updated` はコメント等でも動く（実作業の有無ではない）②「待ち」ステータスの滞留は正常（レビュー待ち等）③大きい課題は長くて当然 |
| 出し方 | しきい値は 18 §1（進行中 7 営業日・Q-022）。「N 営業日 更新なし」と事実で書く。「滞留している」「放置」と書かない |

### 2.2 見積もり乖離
| 項目 | 内容 |
|---|---|
| 判断材料 | 見積もりの変更頻度と幅（プランニング改善の材料） |
| 計算 | スプリント開始時点の SP（`transitions[field=story_points]` のうち開始日以前の最後の `to`。**開始日以前に遷移がなく、開始後にだけ遷移がある課題は、開始後最初の遷移の `from` を開始時点値とする。遷移がまったく無ければ現在の `story_points` を開始時点とみなし、乖離 0 ではなく「変更履歴なし」と書く**）と現在の SP の差。`sprints` が複数ある課題は**現在の `state: active`（無ければ直近終了）のスプリント**の開始日を使い、繰り越しは別に数える |
| 必要 | `story_points` / `transitions[field=story_points]` / `transitions[field=sprint]` / `sprints[].start・state` / `status_category` |
| 誤読リスク | ①SP は相対値でチーム間比較不可②SP 無し（`null`）と 0 は別（06 §1）。`null` は除外して件数を明記③途中で分割した課題は乖離に見える④完了時 SP を後から直す運用だと乖離が消える⑤**スプリントの達成率（完了 SP ÷ 初期 SP）は見積もり乖離とは別物**。チームの成績表として読まれやすいので、この指標群では出さない（出すなら S4 で事実の併記のみ） |
| 出し方 | 差の大きい課題を 3 件までキーで列挙。「見積もりが甘い」と書かない |

### 2.3 スコープ変動
| 項目 | 内容 |
|---|---|
| 判断材料 | スプリント途中の追加・除外の量（S5 ゴール変更判断の材料、S2） |
| 計算 | `transitions[field=sprint]` のうち、スプリント開始後の `at` で入った件数（追加）と出た件数（除外）。SP 合計も併記。繰り越しは別カウント（**同じ課題を追加と繰り越しで二重に数えない**。繰り越し課題は追加から除く）。**開始から猶予日数（既定 1 営業日）以内の変更は計画の一部として除外**（Q-027） |
| 必要 | `transitions[field=sprint]` / `sprints[].start・end・state` / `story_points` |
| 誤読リスク | ①開始直後の整理は変動ではない（猶予で除外）②緊急対応の追加と計画漏れは Jira から区別できない③除外は「完了で抜けた」とは限らない |
| 出し方 | 追加 / 除外 / 繰り越しを別行で。理由は書かない（不明）。聞く問いを添える（「追加分の経緯は？」） |

### 2.4 ブロッカー
| 項目 | 内容 |
|---|---|
| 判断材料 | 他に止められている作業の把握（D4、S1） |
| 計算 | `flagged: true` の課題、および `links[link_type=blocks, direction=inward]` で、塞ぐ側が未完了（`status_category != done`）の課題。塞ぐ側が `done` なら対象外。塞ぐ側が取得範囲外（別プロジェクト）なら「状態不明」と書く |
| 必要 | `flagged` / `links[]` / `status_category` |
| 誤読リスク | ①リンクが貼られていなければ見えない（無いことは安全の証拠ではない）②範囲外は状態不明③`flagged` は付けっぱなしがある（更新なし日数とあわせて見る） |
| 出し方 | 「塞がれている課題 → 塞いでいる課題」の**直接のペア 1 段だけ**を示し、その先の連鎖はたどらない。原因の推測はしない |

### 2.5 担当偏り（分布のみ）
| 項目 | 内容 |
|---|---|
| 判断材料 | 負荷が特定の人に寄っていないかの気づき（S2 の容量材料） |
| 出す条件（固定・Q で調整しない） | 進行中の課題に**異なる担当者が 3 人以上**いること。3 人未満（担当者数が 1〜2）なら**この指標は出さない**。少人数だと集中割合から個人が特定できるため。あわせて**進行中の課題数 N ≥ 5 であること**。担当者が 3 人以上でも N < 5 なら、担当偏りは**何も出さない**（§1 の「N < 5 は件数のみ」の例外。件数も出さない） |
| 計算 | 進行中の課題数・SP 合計について、最大の担当者への集中割合と、担当なし（`assignee_ref: null`）の件数だけを出す |
| 必要 | `assignee_ref`（現在値のみ。遷移は持たない・06 §2）/ `status_category` / `story_points` |
| 誤読リスク | ①課題の大きさ・難しさは課題数に出ない②兼任・サポート作業は Jira に現れない③1 人の休暇で分布が崩れる④「多い人」が成果の多い人とは限らない |
| 出し方 | 出力に載せるのは**集中割合と担当なし件数だけ**。担当者の名前・記号・順位は出さない（14 D3）。structured に `assignee_ref` を持ち込まない（06 §4）。再アサイン履歴の分析はやらない（必要になれば EM 承認で 06 の版を上げる） |

### 2.6 進捗（完了/残 SP・emh-048）
| 項目 | 内容 |
|---|---|
| 判断材料 | S4 チーム向けサマリの「完了/残 pt」（数字は LLM に数えさせない） |
| 計算 | 現在の `state: active` スプリントに属する課題の `story_points` を、`status_category = done` なら完了、それ以外なら残に合算。`null` は除外し件数を明記、`0` は含める |
| 出さないもの | **計画 pt（開始時点 SP の合計）と達成率**。§2.2⑤の方針どおり成績表に読まれるため。S4 テンプレも「計画」を載せない |
| 誤読リスク | ①見積もりの粒度は課題ごとに違う②スプリント途中で除外された課題は含まれない（§2.3 の除外に出る）③残は「未完了の SP」であって必要工数ではない |

## 3. 出力の型（S1 に組み込む）
出力の型の正は [31](31-sprint-health-template.md)。以下は初期案で、食い違いは 31 を優先する。
```
🟡 スプリント健全性: 注意 1 点あり（EM の対応: 1 件確認／判断不要）
観察（<project_alias>・<日付>・進行中 N=12・取得: 完全）
- 更新なし: 進行中 12 件のうち 3 件が 8 営業日以上更新なし（EX-101, EX-104, EX-110）。しきい値 7 営業日
- スコープ: 開始後に追加 2 件(計 5SP)・除外 1 件(2SP)・繰り越し 3 件
解釈の候補
- 追加 2 件は緊急対応、または計画漏れ（どちらかは Jira から分からない）
EM がやること: EX-101 が返答待ちか担当に一言確認（任意）。判断依頼なし
限界: 期間は今スプリント（開始〜今日）。SP 無し 2 件は除外。レビュー待ちの更新なしは正常な場合がある。
```
