# fetcher と analyst / lead の責務境界

状態: ドラフト。背景は [ADR 0002](../adr/0002-cache-schema-and-retention.md)。スキーマは [06](06-cache-schema.md)。

## 原則
**em-fetcher（haiku）は「スキーマのフィールドを埋めるだけ」。** 取得・抽出・書出しは決定的スクリプトが行い、fetcher はそれを実行して結果（成功/失敗 → 件数 → 異常点）を報告する。LLM に項目を埋めさせない（脱落・幻覚の混入を避ける）。
線引きの基準: **同じ入力から誰が実行しても同じ出力になるか**。ならなければ fetcher の仕事ではない。

| fetcher（機械的・決定的） | analyst / lead（判断・解釈） |
|---|---|
| API 呼び出し・ページネーション結合・項目の抽出 | ステータスの意味づけ（「レビュー中」を進行中とみなす等の正規化） |
| 日付の ISO 8601 化・欠損は `null` | 滞留日数・乖離率・スコープ変動の計算（営業日で数えるか、どの遷移を起点とするか自体が解釈） |
| `status` / `status_category` を API の値のまま転記 | 要約・優先度づけ・リスク解釈 |
| `assignee_ref` への変換（HMAC・状態なし） | 担当偏りの読み取り（事実と解釈候補を分ける） |
| Confluence storage 形式 → Markdown の機械変換（変換不能は `unconverted` に記録） | 決定事項・期限・担当の抽出、Jira キー検出と課題への紐付け（structured 工程） |
| JSON Schema 検証、`complete` / `partial_reason` の記録 | 欠損値の補完・推定（`story_points` が無い課題の見積もり等） |
| 失敗・スキーマ不一致を事実のまま報告 | 失敗時の対応判断（再取得するか、指標を断定しないか） |

## 守ること
- `raw` 相当（キャッシュ）と `derived`（計算結果）を分ける。`derived` は後段の決定的スクリプトだけが書き、fetcher は書かない
- スキーマにない項目は足さない。足したくなったら版を上げる提案を em-lead に出す（fetcher が判断しない）
- 推測で補わない。取得失敗・部分取得・スキーマ不一致は握りつぶさず `complete: false` と理由で報告
- 書き込み系 API は使わない。トークン値は出力・ログに出さない（環境変数名のみ）
- 現フェーズは実接続しない。モック（架空サンプル）での整形確認まで
