# 試用 2 週間後の見直し指標の定義

状態: 設計（emh-034。改善ループ提案を管理する部門ボードの項目番号）。しきい値・目安は全て仮置きで、EM が調整する。サンプルは全て架空。L0（読み取り専用。この文書の数え方は何も書き込まない）。

## 結論
- Q-022 / Q-025 / Q-027 / Q-029 が言う「試用 2 週間後に件数を見て調整」を、**何をどこから数えるか** 1 枚にした。EM が指標のためだけに記録することはない（試用開始日を 1 回伝える点だけ例外。§1）
- **試用開始時点で数えられるのは M6 と、M7 の推定版だけ**。実在する監査イベントは `task_updated` / `task_reverted` のみ（`scripts/apply_reply.py`）。M2〜M4 が使う `em_reviewed`・`queue_*` は**承認キューが未実装**のため書かれない。M1 が使う `--ack`/`--snooze` と `data/state/proactive.json` は emh-036 でモック実装済み（監査行は `{at, op, key}`。`first_seen`・`shown_count` は state にある）
- M1・M5 は **Jira 実接続（[09](09-go-checklist.md)）後**に加え、M1 は **Jira 接続後に初めて「放置」が出る**ことも条件（検知スクリプトはモック実装済み）。それまでは「未計測」と書き、0 件とは書かない
- **EM の判断が要る指標は外した**。Q-027 の「追加として数えた件のうち EM が『計画内だった』と判断した割合」は、EM が 1 件ずつ答えない限り数えられない。Q-025 の「EM が `⟦EM が決める⟧` を追記した割合」も同様に直接は数えられず、`edited`（下書きと送った文面が違った）で**代用**する（M2）。いずれも代用であって同じ意味ではない
- 数字は **調整の材料であって原因の説明ではない**（共起と因果を区別する）。しきい値を自動で変えない。変えるかは EM が決める

## 1. 共通ルール
| 項目 | 規則 |
|---|---|
| 期間 | 試用開始日から暦日 14 日（営業日の数は併記）。EM が延ばしたい場合は回答で上書き |
| EM 手入力ゼロの定義 | 指標のために EM が新しく記録・採点・申告をしないこと。EM が普段やる操作（返答の定型語・下書きの送信・`--ack` / `--snooze`）の**結果として残る記録**は使ってよい |
| 分母 | 割合は分母 5 件未満なら「判定不能（分母 N）」と書き、調整の根拠にしない。0 件の割合を 0% と書かない |
| 本文 | 数えるのは件数・id・日付・ハッシュのみ。本文・実名・Jira / Slack の文面は出さない（[05 §3](05-approval-and-audit.md)） |
| 出力 | 指標ごとに「数字 → 分母 → 取れなかった理由（あれば）」の 3 点。解釈は書かない（[14](14-output-quality-checklist.md)） |
| 調整の扱い | 「見直しの目安」は仮置き。目安に当たったら EM に「選択肢 2 つ以内 + おすすめ + 期限」で出す（自動変更しない） |
| 手間削減の検証 | [21 §3](21-approval-queue.md) の所要時間の記録は EM の自己申告が要るので、この文書の対象外（別枠のまま） |
| 試用開始日 | **EM が 1 回だけ伝える（手入力 1 回。この文書で唯一の例外）**。置き場は未決（[20](20-config-and-policy-keys.md) に該当キーが無い）。決まるまでは監査ログの最古の日付を仮の開始日とする |
| 照合不能の扱い | `edited` / `adopted_as_is` は、EM が実際に送った文面のハッシュを取り込みで照合して決まる（Slack 貼り付けの自動照合。[05 §2](05-approval-and-audit.md)。**未実装**）。照合できなかった件は**分母から除き、「照合不能 N 件」として別に出す**（M2・M4 共通。除いた件を採用扱いにも却下扱いにもしない） |
| 設定キー | 見直しの目安・期間は設計書の値で、`config/` のキーとしては**未定義**（[20](20-config-and-policy-keys.md) に無い）。調整は該当 Q の更新で記録し、キー化は必要になった時に別項目 |
| 有効な前提 | M2〜M4 は [Q-025](open-questions.md) が a)（2 週間後に数字で見直す）の場合のみ有効（b は違和感が出た時だけ見直す）。M6・M7 は [Q-029](open-questions.md) の回答後、選んだ選択肢の見直しに使う。どちらも現状は**未回答** |

## 2. 指標一覧
**状態**の凡例: ◎ = 実装済みの記録で数えられる / ○ = 記録の書式は設計済みだが、書き出す実装が未着手（数えられない。M7 は「○（推定のみ）」で、`history` から推定値だけ数えられる）/ △ = Jira 実接続の後（検知スクリプトはモック実装済み）。

| # | 見直す対象 | 何を数えるか | どこから（記録） | 状態 | 見直しの目安（仮置き） |
|---|---|---|---|---|---|
| M1 | Q-022 放置のしきい値（既定 7 営業日） | 試用期間に「放置」ルールが初めて出た key の件数（重複除外）と、そのうち EM が `--ack` / `--snooze` した割合 | `data/state/proactive.json` の `first_seen`・`shown_count`（[18 §3](18-proactive-detection.md)）と、`--ack`/`--snooze` の監査 1 行 | △（Jira 接続後。`proactive_scan.py` はモック実装済み） | 週 0〜1 件 → 据え置き（少なすぎて判断できない）/ 週 2〜5 件 → 据え置いて次の週も見る / 週 5 件超かつ `--ack`/`--snooze` が過半 → 10 営業日へ緩める候補。**件数が多い理由（本当に放置か・しきい値が短いか）は数字から分からないので、EM に問う** |
| M2 | Q-025 一括確認の判定語（**代用**） | 一括確認に入った件のうち、EM が実際に送った文面が下書きと違った（`result=edited`）割合。「`⟦EM が決める⟧` を追記した割合」の**代用** | 監査ログ `em_reviewed` の `result`（[05 §3](05-approval-and-audit.md)）。種別は `queue_item`（下記）。**照合不能は分母から除く**（§1） | ○ | 3 割超 → 判定語の見逃しを疑い、`edited` の件の種別を EM に見せて確認。`edited` は誤字直しも含み、追記と同じではないので断定しない |
| M3 | Q-025 承認キューの上限（個別 5 件） | 個別承認が 5 件を超えて、次回（朝→夕・夕→翌朝）に回した件数と、その発生日数 | 承認キューが出すたびに本文なし 1 行（個別 N・一括 M・持ち越し K）を監査ログへ追記する新イベント `queue_rendered` | ○ | 試用期間の過半の日で持ち越し 1 件以上 → 上限を 6〜7 に上げるか、優先度の帯を見直す候補 |
| M4 | Q-025 検知の質 | 判定語に当たった（コミット候補として `⟦EM が決める⟧` へ移した）件数と、EM が採用した割合（`adopted_as_is` = EM が送った文面が下書きとハッシュ一致。`edited` との和が分母＝照合できた件）。**照合不能は分母から除く** | `queue_item` の `commit_stage`（A/B/C/none）と、`action_id` で突合した `em_reviewed` の `result` | ○ | 検知 0 件が続く → 判定語が効いていない可能性（目視確認。[21 §1](21-approval-queue.md)） |
| M5 | Q-027 スコープ変動の猶予（既定 1 営業日）。EM の判断は使わない**代理指標** | 「追加」として数えた件（猶予の**外**）を、猶予の終わりから **+1 営業日 / +2 営業日 / それ以降**に分けた件数。単位は営業日 | Jira キャッシュの `transitions[field=sprint].at` と `sprints[].start`（[22 §2.3](22-jira-metrics-catalog.md)） | △（Jira 接続後） | +1 営業日に集中（全追加の半数超）→ 猶予を 2 営業日に延ばす候補。ばらつく → 据え置き。**集中は「計画の確定が遅れた」とも「緊急対応」とも読めるので、原因は書かず EM に問う**。猶予内（開始から 1 営業日以内）は定義上除外で常に 0 件のため表に出さない |
| M6 | Q-029 夕方の締めの出し方 | **14 日目時点**で、open/doing・`due` から暦日 3 日超・`due` 以降の `history` に `defer`・`done`・`drop` が無いタスクの件数（スナップショット。累積ではない）。一度 `defer` すると `due` が更新され、新しい `due` から数え直す | tasks の `history`・`due`（[25](25-evening-wrapup.md) と同じ） | ◎ | 0 に近い → b)（無い日は出さない）へ寄せる候補。多い → a)（毎日出す）を維持。**0 に近いのは「夕方が不要」とも「夕方レポートに関係なく処理されている」とも読め、夕方レポートの効果とは言えない**（共起を原因にしない） |
| M7 | Q-029 判断依頼の効き（**推定版のみ**） | `defer` 2 回目の日（[25](25-evening-wrapup.md) で判断依頼が出る条件に入った日）を「出たはずの日」とみなし、翌日末までに同じタスクの `history` に `done` / `drop` があった割合（`due` 変更は返答に数えない。先送りは判断の回避でも起こり、答えたとは言えないため） | tasks の `history`（`at`）。**判断依頼が実際に表示された日は、どこにも記録されない**（夕方レポートは何も書き込まない） | ○（推定のみ） | 半数未満 → 判断依頼の書き方・件数を見直す候補（原因は問う）。**限界**: ① 表示日は推定 ② `drop` は返答の定型語 5 種に無く（[24](24-reply-apply.md) で未決）、EM の手編集でしか `history` に残らない ③ 「分割」は `history` で判別できない。表示 id を記録する実装は別項目 |

- M1・M5 は接続前は**未計測**。試用開始時に数えられるのは M6 と M7（推定版）。M2〜M4 は承認キューと照合の実装後
- `queue_rendered` / `queue_item` は**この文書で書式だけ決める**（承認キューの実装は未着手）。本文・実名は含めない。`kind` の語彙は [12](12-secretary-job-list.md) / [21](21-approval-queue.md) の下書き種別（`slack_reply` / `jira_comment` / `minutes` / `retro_agenda` 等）で、未実装のため実装時に確定する。`queue_item` は `result` を持たず、`action_id` で `em_reviewed` と突合する（結果を二重に持たない）。[05 §3](05-approval-and-audit.md) の `event` 一覧にも追記した:

```json
{"ts":"2026-01-01T09:00:00+09:00","event":"queue_rendered","slot":"morning","individual":5,"bulk":2,"carried_over":1}
{"ts":"2026-01-01T09:00:00+09:00","event":"queue_item","action_id":"a-0001","slot":"morning","bucket":"bulk","kind":"slack_reply","commit_stage":"none"}
```

## 3. 見直しの回し方
1. 試用 14 日目に、§2 の定義で集計する。集計スクリプトは**未実装**（必要になった時点で別項目にする）。当面は監査ログ・tasks・state を読んで数えても、定義どおりなら同じ結果になる
2. 結果は指標ごとに「数字・分母・取れなかった理由」で出し、目安に当たったものだけ「選択肢 2 つ以内 + おすすめ + 期限」で EM に出す
3. 調整は [open-questions.md](open-questions.md) の該当 Q を更新して記録する

## 4. 限界
- 14 日間・EM 1 人の数字は小さい。分母 5 件未満を判定不能にしているのはそのため。目安は**調整の入口**で、正解ではない
- `edited` は誤字直しを含み、EM の意図（追記した / 直しただけ）は読み取れない。また `edited` の判定は送信文面の自動照合（未実装）が前提
- M7 は推定。M1・M5 は Jira 実接続の GO が前提（M1 の検知実装は済み）。接続が遅れれば、見直しは M6・M7 と（実装後の）M2〜M4 だけで先に行う
