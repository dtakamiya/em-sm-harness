# 試用 2 週間後の見直し指標の定義

状態: 設計（emh-034。改善ループ提案を管理する部門ボードの項目番号）。しきい値・目安は全て仮置きで、EM が調整する。サンプルは全て架空。L0（読み取り専用。この文書の数え方は何も書き込まない）。

## 結論
- Q-022 / Q-025 / Q-027 / Q-029 が揃って言う「試用 2 週間後に件数を見て調整」を、**何をどこから数えるか** 1 枚にした。数えるのは既存の記録（`data/audit/`・tasks の `history`・`data/state/`）だけ。EM が指標のためだけに記録することはない
- **EM の判断が要る指標は外した**。Q-027 の「追加として数えた件のうち、EM が『計画内だった』と判断した割合」は、EM が 1 件ずつ答えない限り数えられない。代わりに Jira の記録だけで数える **代理指標**（§2 M5）を置く
- **試用開始時点で数えられるのは tasks と監査ログの分だけ**。Jira の滞留・スコープ変動は実接続（[09](09-go-checklist.md)）の後でないと数えられない（キャッシュが無い）。それまでは「未計測」と書き、0 件とは書かない
- 数字は **調整の材料であって原因の説明ではない**（共起と因果を区別する）。しきい値を自動で変えない。変えるかは EM が決める

## 1. 共通ルール
| 項目 | 規則 |
|---|---|
| 期間 | 試用開始日から暦日 14 日（営業日の数は併記）。EM が延ばしたい場合は回答で上書き |
| EM 手入力ゼロの定義 | 指標のために EM が新しく記録・採点・申告をしないこと。EM が普段やる操作（返答の定型語・下書きの送信・`--ack` / `--snooze`）の**結果として残る記録**は使ってよい |
| 分母 | 割合は分母 5 件未満なら「判定不能（分母 N）」と書き、調整の根拠にしない。0 件の割合を 0% と書かない |
| 本文 | 数えるのは件数・id・日付・ハッシュのみ。本文・実名・Jira / Slack の文面は出さない（[05 §3](05-approval-and-audit.md)） |
| 出力 | 指標ごとに「数字 → 分母 → 取れなかった理由（あれば）」の 3 点。解釈は書かない（[14](14-output-quality-checklist.md)） |
| 調整の扱い | 「見直しの目安」は仮置き。目安に当たったら EM に「選択肢 2 つ以内 + おすすめ + 期限」で出す（自動変更しない） |
| 手間削減の検証 | [21 §3](21-approval-queue.md) の所要時間の記録は EM の自己申告が要るので、この文書の対象外（別枠のまま） |

## 2. 指標一覧
**状態**の凡例: ◎ = 今ある記録だけで数えられる / ○ = 数える記録は設計済みだが、書き出す実装がまだ / △ = Jira 実接続後。

| # | 見直す対象 | 何を数えるか | どこから（記録） | 状態 | 見直しの目安（仮置き） |
|---|---|---|---|---|---|
| M1 | Q-022 放置のしきい値（既定 7 営業日） | 試用期間に「放置」ルールが初めて出た key の件数（重複除外）と、そのうち EM が `--ack` / `--snooze` した割合 | `data/state/proactive.json` の `first_seen`・`shown_count`（[18 §3](18-proactive-detection.md)）。`--ack`/`--snooze` は監査ログに 1 行 | △（Jira キャッシュ前提） | 件数が週に 5 件を超え、かつ `--ack`/`--snooze` が過半 → 10 営業日へ緩める候補。0〜1 件 → 据え置き（件数が少なすぎて判断できない） |
| M2 | Q-025 一括確認の判定語 | 一括確認に入った件のうち、EM が実際に送った文面が下書きと違った（`result=edited`）割合 | 監査ログ `em_reviewed` の `result`（[05 §3](05-approval-and-audit.md)）。一括確認の件は承認キューが `queue_item` で印を付ける（M4 と同じ新イベントで書く） | ○ | 3 割超 → 判定語の見逃しを疑い、`edited` の件の種別を EM に見せて確認。**`edited` は『`⟦EM が決める⟧` を追記した』と同じではない**（誤字直しも含む）ため、断定せず確認の入口にする |
| M3 | Q-025 承認キューの上限（個別 5 件） | 個別承認が 5 件を超えて、次回（朝→夕・夕→翌朝）に回した件数と、その発生日数 | 承認キューが出力するたびに、本文なしの 1 行（個別 N・一括 M・持ち越し K）を監査ログへ追記する（新イベント `queue_rendered`。実装は承認キュー実装の時） | ○ | 試用期間の過半の日で持ち越し 1 件以上 → 上限を 6〜7 に上げるか、優先度の帯を見直す候補 |
| M4 | Q-025 同上（検知の質） | 判定語に当たった（コミット候補として `⟦EM が決める⟧` へ移した）件数と、EM が採用した割合 | `queue_item`（種別・検知段 A/B/C・結果。本文なし） | ○ | 検知 0 件が続く → 判定語が効いていない可能性（試用で目視確認。[21 §1](21-approval-queue.md)） |
| M5 | Q-027 スコープ変動の猶予（既定 1 営業日） | 「追加」として数えた件（猶予の外）を、開始からの日数で 1 営業日目 / 2 営業日目 / 3 日目以降に分けた件数。**EM の判断は使わない代理指標** | Jira キャッシュの `transitions[field=sprint].at` と `sprints[].start`（[22 §2.3](22-jira-metrics-catalog.md)） | △ | 2 営業日目に集中（全追加の半数超）→ 猶予を 2 営業日に延ばす候補。ばらつく → 据え置き。**集中は「計画が遅れて確定した」とも「緊急対応」とも読めるので、原因は書かず EM に問う** |
| M6 | Q-029 夕方の締めの出し方 | 持ち越しのまま 3 日を超えたタスクの件数（`history` に `defer`・`done`・`drop` のいずれも無いまま `due` から 3 日超） | tasks の `history`・`due`（[25](25-evening-wrapup.md) と同じ） | ◎ | 0 に近い → b)（無い日は出さない）へ。多い → a)（毎日出す）を維持 |
| M7 | Q-029 / 判断依頼の効き | 判断依頼（先送り 3 回目・昇格）が出た日から翌日末までに、EM の返答（定型語）が来た割合 | tasks の `history`（`defer`/`drop`/`done`）と監査ログ `task_updated`（[24](24-reply-apply.md)） | ◎ | 半数未満 → 判断依頼の書き方・件数を見直す候補（原因は問う） |

- 「Jira 実接続後」の △ は、接続前は**未計測**。接続前の試用では M1・M5 の欄に「未計測（接続前）」と書く
- M2〜M4 の `queue_item` / `queue_rendered` は**この文書で書式だけ決める**（承認キューの実装は未着手）。実装時にこの形で書き出す。本文・実名は含めない。形式（既存の監査ログに揃える）:

```json
{"ts":"2026-01-01T09:00:00+09:00","event":"queue_rendered","slot":"morning","individual":5,"bulk":2,"carried_over":1}
{"ts":"2026-01-01T09:00:00+09:00","event":"queue_item","action_id":"a-0001","slot":"morning","bucket":"bulk","commit_stage":"none","result":"edited"}
```

## 3. 見直しの回し方
1. 試用 14 日目に、§2 の定義で集計する。集計スクリプトは**未実装**（必要になった時点で別項目にする）。当面は監査ログ・tasks・state を読んで数えても、定義どおりなら同じ結果になる
2. 結果は指標ごとに「数字・分母・取れなかった理由」で出し、目安に当たったものだけ「選択肢 2 つ以内 + おすすめ + 期限」で EM に出す
3. 調整は [open-questions.md](open-questions.md) の該当 Q を更新して記録する（既定値の変更は `config/` の該当キーのみ。[20](20-config-and-policy-keys.md)）

## 4. 限界
- 14 日間・EM 1 人の数字は小さい。分母 5 件未満を判定不能にしているのはそのため。目安は**調整の入口**で、正解ではない
- 監査ログの `edited` は誤字直しを含み、EM の意図（追記した / 直しただけ）は読み取れない
- M1・M5 は Jira 実接続の GO（[09](09-go-checklist.md)）が前提。接続が遅れれば、見直しは tasks と監査ログ由来の M2〜M4・M6・M7 だけで先に行う
