# Slack 抽出観点ガイド（判定基準・境界例・抽出例）

状態: ドラフト（設計のみ・emh-006）。[13](13-slack-paste-input.md) §6 のスキーマに対する「何を抽出し、何を抽出しないか」の観点。Slack への接続・書き込みはしない。サンプルはすべて架空（`member-a` 等）。

## 1. 原則
- **取りこぼしを選ぶ**: 迷ったら抽出しない（誤抽出は EM の信頼を落とす。13 §4 と同じ）
- **根拠なしは出さない**: `evidence.quote`（40 字以内・匿名化済み原文の部分文字列）が取れない項目は作らない
- **観察と解釈を混ぜない**: `observation` は発言の言い換えのみ。評価語・原因・性格の推測を入れない（[14](14-output-quality-checklist.md)）
- **EM に効く順**: ①EM 宛ての依頼 ②障害物 ③決定 ④リスク ⑤感情の兆候（最も誤読しやすいので最後・最も厳しく）

## 2. 種別ごとの判定基準
| kind | 抽出する（目印） | 抽出しない |
|---|---|---|
| `request` | 宛先が EM と読める（`em` への呼びかけ・「確認待ち」「相談できますか」）。期限語は `due_raw` に原文のまま | 宛先不明の質問（誰に向けたか読めない）。雑談の「〜できたらいいね」 |
| `blocker` | 本人が「待ち」「止まっている」と述べている | 第三者が「止まっているはず」と推測した発言。遅れの事実だけで本人が言っていないもの |
| `decision` | 「決まりました」「〜に回します」等の**確定表現**。承認者が読めれば `decided_by` | 提案・相談・「〜にしましょうか」。確定表現があっても疑問形なら対象外 |
| `risk` | 将来への懸念の**発言そのもの**（「〜が残っている気がします」） | 秘書側の「これはリスク」という判断。事実の遅れ（それは blocker か Jira 指標の役目） |
| `signal` | 負荷・困惑・不満・前向きさを示す**表現**（「また夜中まで」） | 絵文字だけ・皮肉か判別できない発言・業務の事実だけの発言。人事・機微語を含むファイル（13 §8 でスキップ済み） |

### 同一発言が複数種別に当たるとき
- 1 発言から複数 item を出してよい（例: 懸念 + 相談依頼 → `risk` と `request`）。ただし各 item に別々の `quote` を付ける
- 同じ内容の言い直しは 1 件にまとめる（スレッド内の繰り返しで件数を水増ししない）

## 3. confidence の付け方
| 値 | 条件 | 下流 |
|---|---|---|
| `high` | 明示的な表現（「決まりました」「確認待ちです」） | candidates に流してよい |
| `medium` | 宛先や対象は読めるが、依頼か雑談かが文脈依存 | candidates に流す（EM が確定） |
| `low` | 文脈からの推定 | 流さない・`notes` に残すのみ |

`signal` / `risk` は解釈を含むため原則 `medium`（明示的な本人の言明でも `high` にしない）。

## 4. 誤読リスクと対策
| 誤読 | 対策 |
|---|---|
| 「また夜中まで」→「疲れている人」 | `signal` は表現のみ記録。`interpretation_candidates` に 2 つ並べ、確かめ方を添える（13 §7）。個人別の時系列は作らない |
| 後続発言を原因扱い（「A の後に B」→「A が原因」） | 時系列は `observation` に書かない。因果語（〜のせいで・〜ため）を使わない |
| 提案を決定扱い | 確定表現のみ `decision`。迷えば抽出しない |
| 宛先の取り違え | `to_em` は `em` への明示がある場合のみ true。不明は `request` を作らない |
| 担当・期限の補完 | 原文にないものは空欄 + `notes`。`due_raw` を日付に直すのは candidates 作成時（曖昧なら null） |

## 5. 抽出例（架空サンプル）
入力: `tests/fixtures/sample-week/slack/` の 2 件。期待出力: `tests/fixtures/slack-extraction/expected.json`（匿名化後ハンドル `m_a1a1a1` 等は例示用の架空値）。検証は `tests/test_slack_extraction.py`。`excluded` は fixture 専用の注記で、本番のスキーマ（13 §6）には出力しない。

| 貼り付け | 発言 | 結果 | 理由 |
|---|---|---|---|
| 10/05 | member-a「環境は誰が用意しますか？」 | **抽出しない**（`excluded`） | 宛先が読めない質問。同スレッドの member-b 発言が EM 宛ての依頼として出る |
| 10/05 | member-b「em さんに確認待ちです。金曜までに決めたい」 | `request`（`to_em: true`・`due_raw: 金曜まで`・high） | EM への明示 + 期限語 |
| 10/05 | member-c「staging のデータ待ちで止まっています」 | `blocker`（`EX-101`・high） | 本人が「待ち・止まっている」と述べている |
| 10/07 | member-b「見積もりの件、決まりました。EX-102 は次スプリントに回します（member-a 承認済み）」 | `decision`（`decided_by: member-a`・high） | 確定表現 + 承認者が読める |
| 10/07 | member-c「また夜中までかかりました。明日の午前は動けるか分かりません」 | `signal`（fatigue）。「明日の午前は〜」は別 item にしない | 解釈候補 2 つ + 確かめ方。後半は発言者本人の見込みで、リスク断定の材料にしない |
| 10/07 | member-a「リスクが残っている気がします。em さん、相談できますか」 | `risk` + `request`（`to_em: true`・medium） | 懸念の発言そのもの + EM への相談依頼。期限語なし → `due_raw: null` |

## 6. 品質チェック（抽出スキルの出力に対して・受入基準）
- [ ] 全 item に `quote`（40 字以内・原文の部分文字列）がある
- [ ] `actors` はハンドルのみ（実名・メンション表記が残っていない）
- [ ] `interpretation_candidates` は `signal` ちょうど 2 件、`risk` は 0〜2 件、他の種別は空（13 §6 と同じ）
- [ ] `observation` に評価語・因果語・補完（担当・期限・理由の推測）がない
- [ ] `low` を candidates に流していない

## 8. 自動評価（emh-031）
抽出スキルの出力を期待値と突き合わせ、改善ループの物差しにする。ローカルのみ・読み取り専用。

```
python3 scripts/eval_slack_extraction.py <構造化 JSON またはディレクトリ> [--expected tests/fixtures/slack-extraction/expected.json] [--min-recall 0.8] [--max-extra 0]
```
- 突き合わせの鍵は `(kind, evidence.msg_index, actors.from)`。文言（`observation` / `quote`）の揺れは数えない
- 出力: 再現率（期待のうち拾えた割合）・誤抽出（期待にない item の件数。うち `excluded` の発言から出たもの）・精度・`confidence` / `to_em` の食い違い件数
- 終了コード: 0=OK / 1=`--min-recall` または `--max-extra` の基準割れ / 2=入力不正
- 同梱の `skills/slack-to-candidates/examples/` は再現率 100%・誤抽出 0 が基準（回帰の確認）
- 限界: 期待値は架空サンプル 2 件・計 6 item。判定の鍵が粗いので、品質の最終判断は §6 のチェックと EM のレビューで行う
