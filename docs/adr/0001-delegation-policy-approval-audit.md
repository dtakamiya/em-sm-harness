# 0001. 委任ポリシー・承認フロー・監査ログの方式

- 状態: 提案（Ryoko の design-review 判定待ち）
- 日付: 2026-10-03
- 関連: emh-013 / docs/design/03-secretary-model.md / docs/design/05-approval-and-audit.md / policy/delegation.yaml

## 背景・決めること
L2（事前承認ルールによる代行実行）を後から安全に足せるよう、(A) ポリシーの構造、(B) 承認フロー、(C) 監査ログを先に固める。
制約: 現フェーズは L1、書込は実装しない、実接続なし、会社固有情報は repo に入れない。

## 案
### 案A（出した人: em-builder 役）
- ポリシー: アクション種別 × `sensitivity` タグの二層。`default: deny`、`hard_deny_tags`、`grants`（追記で L2 付与）。lint で hard_deny に触れる grants を弾く
- 承認: `drafted → em_reviewed → em_sent`。送信結果は EM が CLI で手動記録。L2 は `dry_run → diff → 承認(content_hash 束縛) → 実行`。影子運用
- 監査: `data/audit/YYYY-MM.jsonl`、本文は持たずハッシュ。ハッシュ連鎖は L2 から必須
- 懸念: タグ付けは秘書の自己申告。手動記録は負担と漏れ

### 案B（出した人: em-sm-analyst 役）
- ポリシー: 種別ごとに `l2_eligible`。初期は全種別 L1。L2 候補は3つのみ。4問チェック（可逆性/影響範囲/リスク/なりすまし感）。`hard_block` に理由付き
- 承認: 朝夕の承認キュー1枚（最大5件・一括確認欄）で承認疲れを防ぐ。無修正採用の連続で昇格を提案。KILL ファイル、期限切れは自動 L1、EM 不在は溜めるだけ
- 監査: 日次ファイル。サマリ1行。本文は記録しない。送信結果は次回取り込み時に自動照合
- 懸念: 種別軸のみでは「評価を含む jira.comment」を防げない。「迷う」は主観

## 批評（互いの案への指摘）
- A への指摘（B 担当から）: 手動記録が重い／タグ自己申告の漏れが穴（タグ無し = 安全にしない）／承認疲れ対策が無い／不在時・KILL が無い
- B への指摘（A 担当から）: 種別軸だけでは内容の機微を捕まえられない／4問目（EM が自分で書いたと言えるか）は主観で機械判定不可／「無修正連続 = 昇格」はゴム印と区別できない／サマリを先頭に置くと追記専用と衝突

## 決定
**案A（二層ポリシー）を骨格に、案B の運用面（承認キュー・KILL・不在時・自動照合・日次サマリ別ファイル）を取り込む。**
1. 判定は種別 × sensitivity タグの2軸。`default: deny`、タグ無し・不明は L1 止まり（「タグ無し = 安全」にしない）
2. L2 は種別だけでなく `scope`（テンプレ ID + 固定宛先）で縛る。秘書の自由文は L2 にしない（タグ漏れが事故に直結しない）
3. 4問チェックは機械判定でなく、EM が grants を足すときの判断ガイド（yaml コメント）に格下げ
4. L2 昇格は秘書が提案のみ。無修正採用率だけでなく件数・修正率・確認時間で見る。付与は EM のみ
5. 送信結果は自動照合を主、EM の任意報告を補助（EM 回答済み 2026-10-03: 自動照合）
6. 監査は日次 jsonl・本文なし・サマリは別ファイル。ハッシュ連鎖は L2 付与時に必須
7. 合意: fail-closed（期限切れ・上限超過・KILL・不在 → L1）、`content_hash` 承認束縛、影子運用、L1 から監査を取る

em-lead 集約。Ryoko の design-review 判定: **条件付き GO**（2026-10-03）。根拠: fail-closed・本文なし監査・grants 空で現状 L1 を維持でき、委任ラダーの逸脱なし。条件: (1) EM が Q-004/Q-005 に回答 (2) 最初の grants 付与前に policy lint（emh-022）を用意 (3) 採用ステータスへの更新は EM のマージ後
