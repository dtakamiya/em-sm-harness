# ステークホルダー報告の下書き（R1/R2）

用語: **L1** = 委任ラダー最下段（下書きまで・送信と書込は EM）、**共起** = 同じ時点に並んで出ただけで原因とは限らない関係、**R1** = 報告の下書き、**R2** = 報告前の事実確認リスト（数字・日付の出典）、**R3** = 上長・他部門への約束・期限の提示（常に EM が決める）、**12** = 秘書の仕事一覧の設計書（R1〜R3 の定義）、**14** = 出力品質基準、**出典** = その数字・日付を確かめられる課題 ID・取得日・キャッシュ名。

設計: `docs/design/12-secretary-job-list.md` §3.4 / 型: `templates/drafts/stakeholder-report.md` / 品質基準: `docs/design/14-output-quality-checklist.md`

## 手順
1. 入力を集める（EM が貼る箇条書き、または `data/jira-cache/<alias>/<YYYY-MM-DD>.json`〔`docs/design/06-cache-schema.md` §2 準拠・読み取り専用〕）。各行を「達成 / 未達・遅れ / リスク候補」に分け、**出典が付かない行は事実に入れない**
2. 出典がない数字・日付は本文から外し、末尾の事実確認リストに `[ ] 出典未確認:` として回す（推測で埋めない）
3. `templates/drafts/stakeholder-report.md` の型（順序・上限・書式はテンプレが正）に流し込む。ここでの注意は 2 点だけ
   - 🔴 は EM が付ける候補として書き、秘書は断定しない
   - 見通しは断定しない。共起を原因と書かない
4. **約束になる日付・スコープは本文に書かず** `⟦EM が決める⟧` に候補として寄せる（R3 = 新規コミットは EM）
5. R2 の事実確認リストを別添する。本文の数字・日付 1 つにつき 1 行（下の「出典チェックリスト」）
6. 内部点検（合否は出力に載せない）: 冒頭 `【下書き・未送信】` / 本文の数字・日付すべてが出典付きか事実確認リスト入り / 約束の日付が本文にない / 人名・個人別の並びがない / 60 秒で読める量（本文 600 字以内。テスト `test_body_within_limit_and_risks_at_most_three` が見本で検証）
7. EM に 1 枚を返す。前置き・経緯説明は不要。送信・共有は EM

## 出典チェックリスト（R2）
各行は `- [ ] {数字/日付}: 出典={課題ID・取得日・キャッシュ名} / 確認={EM が見る場所}` の形。
- 数字（件数・達成率）は分母と取得日を併記する。分母が不明なら「分母未確認」と書く
- 日付は「完了日」「予定日」「取得日」のどれかを明記する（予定日は事実でなく見込み）
- キャッシュが古い（取得日が報告期間の終了日より前）場合は先頭に「再取得推奨」を 1 行足す
- 出典を確かめられないものは `出典未確認` とし、本文では「未確認」と書く

## 受け入れ基準（EM の手間が実際に減るか）
- 基準: EM が下書きに入れる直しが **頭 1 行（状態語と結論）と `⟦EM が決める⟧` の記入だけ**で済む。出典の差し戻し・数字の書き直しが要るなら不合格
- **未決事項（マージ後）**: 上は見本（架空）での想定で、実運用では未検証。EM が実案件で 1〜2 回試し、直しの量を判定する。結果で本文の型を直す
- 本文に出典のない数字・日付が残らないことはテスト `test_body_numbers_have_source_or_checklist` が見本で検証

## してはいけないこと
- Jira / Confluence / Slack への書き込み・送信・接続、実データ・実名のコミット
- 約束・期限・スコープ変更の本文への記載（R3 = EM）。出典のない数字を本文に置くこと
- 原因の断定、評価語、担当者名・個人別の並び
- 実接続やトークンの使用（現フェーズは設計のみ）

## 試す
`examples/input.sample.md`（架空の箇条書き）を流し込むと `examples/expected-output.md` になる。出典のない 1 行（`連携先の準備は順調らしい`）は本文に入らず、事実確認リストの `出典未確認` に回る。
